## Executive summary

Full sync already avoids reading or parsing files whose stored size and mtime match, but still enumerates the checkout, materializes multiple whole-inventory collections, and makes duplicate synchronous metadata probes for most tracked files. SQLite already has an indexed file inventory; it lacks a durable directory/discovery inventory and a granular run checkpoint for explicit rebuilds. Start by preserving the last good graph when a source mount is uncertain, reducing unnecessary reads, and changing the background default to 600 seconds without rewriting explicit user settings. Then build bounded stored-first reconciliation, and introduce generation-based resume only where measurements justify its extra disk and write costs. This is source-backed prioritization, not a measured speedup on the target machine.

## Findings and options

### High

#### CGIO-01 | A missing/unavailable source path can be interpreted as a deletion

**Confirmed behavior, high confidence; deployment incident not observed.** Expected: publish removals only on authoritative evidence, and keep the last graph if the mount cannot be checked. Actual: full reconciliation marks DB rows absent if they are absent from the scan or `existsSync()` returns false, then deletes them; this path does not classify errors. Scoped discovery also uses `existsSync()`. `statSync` errors elsewhere are recorded instead. An incomplete listing or temporarily unreachable subtree could affect many rows, so impact and urgency are high for this deployment. Sources: `src/extraction/index.ts:1613`, `:4010`, `:4057`, `:4082`, `:4102`, `:4131`.

| Option | Approach | Pros | Cons and risks | Effort/complexity | Expected benefit |
| --- | --- | --- | --- | --- | --- |
| A | Single typed stat per candidate, explicit enumeration completeness, root identity and per-subtree sweep eligibility | Keeps last good rows; eliminates duplicate probe | Must preserve inaccessible-vs-missing semantics through fallback, symlinks, deletions and races | Medium | Prevent broad false removal and cut metadata calls |
| B | Stage a complete generation and publish only when root/scope/coverage are valid | Clear publication boundary and reader semantics | More SQLite I/O and disk; still needs typed scan failures; slower feedback | High | Stronger fail-closed rebuild and recovery |

**Recommend A first.** Recheck root/fingerprint before deletion, do not treat `EIO`, `ESTALE`, or permission failures as absence, and don't infer deletion from a partial scan or an unexpectedly replaced mount. Explicitly distinguish a validated scope exclusion from a missing path. Test actual deletions, mount replacement, and unreachable subtrees without live remote access.

#### CGIO-02 | Full sync is inventory-wide even when almost nothing changes

**Confirmed scalability issue, high confidence; time share unmeasured.** Expected target: prioritize known files and avoid discovering or parsing entries already proven current. Actual: broad Git enumeration with fallback, `SELECT *` materialization, then file array, set, map and synchronous metadata loops; this is O(N) remote metadata requests and O(N) application inventory memory. Known-current files already skip reads/hash/parse. The existing `files` table stores path, hash, size, mtime, indexed time and error state; no dedicated persistent directory/scan inventory appears in the inspected schema. A clean Git status alone is not proof for untracked, ignored opt-ins, branch switches or live edits. Source: `src/extraction/index.ts:1396`, `:3924`, `:4031`, `:4082`, `:4126`; `src/db/schema.sql:67`; `src/db/queries.ts:4277`.

| Option | Approach | Pros | Cons and risks | Effort/complexity | Expected benefit |
| --- | --- | --- | --- | --- | --- |
| A | Expose scoped sync for a trustworthy change manifest; retain periodic full repair | Reuses existing behavior; small change set approaches O(k) validation | Requires complete change source including deletes/renames and gaps; non-authoritative batches must fall back | Medium | Fewer remote operations following known updates |
| B | SQLite directory inventory + bounded stored-first reconciliation overlapping discovery | Fits varied sources; avoids O(N) JS materialization and repeated enumeration where complete change evidence exists | Additive schema/migration and state machine; without trustworthy evidence still O(N) I/O | High | Lower peak inventory memory and faster time to first verified update |
| C | Operate on an encrypted local mirror with an explicit refresh pipeline | Eliminates network metadata round trips in normal operations | Extra disk and mirror consistency; deployment choice, not a feature fix | Medium operational | Potentially largest immediate remote-I/O reduction |

**Recommend B as the target, A as an independently useful first increment if a complete feed exists.** Prefer primary-key keyset pages with minimal projections; avoid keeping a SQLite read cursor/transaction open across remote awaits. Only use incremental short-circuits where coverage is proven. Reuse existing `files` rows instead of copying them; avoid updating every unchanged row just to mark it seen.

#### CGIO-06 | Synthesis input discovery attempts to read every indexed source

**Confirmed source work, high confidence; workload share unmeasured.** Expected: reuse compatible source facts and avoid reading ineligible inputs. Actual: `collectInputs` calls `ctx.readFile` before applying its pattern gate, including candidates that produce no edges; cache misses read disk and pooled passes may read again. This adds Θ(F) lookups and bytes proportional to cache misses whenever whole-project synthesis runs. Wide reach on remote storage justifies high priority; this is not a claim that every sync runs synthesis. `src/resolution/callback-synthesizer.ts:5628`, `src/resolution/index.ts:828`.

| Option | Approach | Pros | Cons and risks | Effort/complexity | Expected benefit |
| --- | --- | --- | --- | --- | --- |
| A | Apply provably equivalent language/path gates before reads | Small, bounded change | Less gain in homogeneous repos; gates must not omit dependency inputs | Small–medium | Avoid reads for known-ineligible paths |
| B | Persist versioned pattern facts when source is already in hand; discover indirect dependencies for positive facts | Reuses extraction/changed-file reads and survives restart | Invalidating rules and positive/negative facts correctly is harder; adds writes | Medium–high | Avoid recurring whole-project pattern reads |

**Recommend A as a parity-checked probe, then B if tracing confirms material I/O.** Preserve inputs that emitted no edges due to caps, lazy modules and re-export dependency tracking. Compare exact input rows/edges and cold/warm source opens, bytes and wall time.

### Medium

#### CGIO-03 | Interrupted runs recover work, but cannot reliably restart at a durable phase/batch boundary

**Confirmed requirement gap versus requested behavior, high confidence.** Current `index` explicitly recreates the database; `index_state`, persisted file rows and unresolved refs, `synthesis_pending`, and index repair let a later sync recover portions. There is no inspected per-run queue/cursor whose commit is coupled to graph changes, and the fresh-build durability optimization is incompatible with a claim that every acknowledged checkpoint survives a crash. High restart cost on large jobs, but no claim of lost source data. Sources: `src/bin/codegraph.ts:956`, `src/index.ts:686`, `:724`, `:1248`, `:1904`, `src/extraction/index.ts:3475`, `src/db/schema.sql:79`.

| Option | Approach | Pros | Cons and risks | Effort/complexity | Expected benefit |
| --- | --- | --- | --- | --- | --- |
| A | Add explicit `resume` for interrupted work using committed file state and idempotent phase markers; verify filenames and fingerprints again | Smallest practical recovery improvement; preserves clean rebuild semantics | May repeat discovery or tail phases; partial index visibility needs a documented policy | Medium–high | Avoid replaying many committed parses |
| B | Run/phase journal and staged rebuild generation; durable checkpoints per ordered batch with explicit publication | Resumes a verified frontier, retains previous graph for readers | Schema/versioning, disk for two generations, writes and publication/recovery complexity | High | Bounded replay and last-good serving during rebuild |
| C | Content-addressed extraction cache for resumability across generations | Reuses costly parse results across rebuilds | Duplicates storage, requires correct path/config/grammar cache keys and eviction; does not itself resume resolution | High | Optional if parse is measured as dominant |

**Recommend A, designed so B remains possible.** For new semantics, checkpoint graph writes and completion together; avoid `MEMORY/OFF` in checkpointed mode. Distinguish process restart from power-loss durability, and verify identical graph results and order after interruption. Do not silently change destructive `index` semantics; define an explicit resume path.

#### CGIO-05 | Sync repeats I/O for touched-but-unchanged files and can reread changed source

**Confirmed redundant work, high confidence; target frequency unmeasured.** Expected: one validated observation advances unchanged metadata; a changed input is handed to extraction without a mandatory repeat read. Actual: matching bytes in the changed-metadata path do not advance `modified_at`, so the next full sync can repeat the hash/read. Changed files enter a path-only queue and `indexFile` reads them again. This is bounded to candidates, but checkout tools that touch many files can amplify it. Source: `src/extraction/index.ts:4126`, `:4144`, `:4163`, `:4206`, `:3325`.

| Option | Approach | Pros | Cons and risks | Effort/complexity | Expected benefit |
| --- | --- | --- | --- | --- | --- |
| A | Batch conditional metadata-only updates after hash equality and a coherent file observation | Avoids successive no-op reads without changing graph | Adds local SQLite writes on touch bursts; prevent blessing mismatched bytes/stat or clearing error state | Small–medium | No repeated read/hash for timestamp-only touches |
| B | Pass verified stat and content into extraction through a byte-bounded queue; revalidate races | Usually one content read for a changed file | Increases retained content; needs byte backpressure, ownership and atomic error handling | Medium | Fewer remote reads on edit-heavy sync |

**Recommend A first.** Defer B until remote read counts justify it; use the same bounded observation primitives as CGIO-01.

#### CGIO-07 | Read/parse/store admission is count-bounded, not byte-bounded

**Confirmed, high confidence; actual idle/RSS cost unmeasured.** A ten-file `Promise.all` waits for the slowest read before dispatch; ordered parsing and up to 64 unacknowledged store bundles bound counts but not extracted payload bytes. Large extracted results and remote-tail reads make this material in full builds, not no-op sync. `src/extraction/index.ts:2723`, `:2742`, `:2919`; `src/file-limits.ts:72`.

| Option | Approach | Pros | Cons and risks | Effort/complexity | Expected benefit |
| --- | --- | --- | --- | --- | --- |
| A | Prefetch one byte-bounded next batch while parsing the current batch | Limited blast radius; can measure quickly | Within-batch barrier remains | Medium | Overlap source I/O without unbounded read-ahead |
| B | Rolling byte-credit pipeline with ordered commit and a largest-item allowance | Reduces barriers and caps payload accumulation across stages | More backpressure, failure and sequencing complexity | High | Better worker utilization and lower peak payload memory |

**Recommend A if profiling finds stalled workers; B only if the barrier remains material.** Inject slow and high-symbol files; compare RSS, idle time, throughput and exact graph/order.

#### CGIO-08 | Resolver workers replicate graph-wide membership caches

**Confirmed, high confidence; byte impact unmeasured.** Each warmed resolver retains file-path and distinct-name sets. With W workers, F paths and U names, this is O((W+1)(F+U)) retained entries before private variable-size caches. Indexed lookups already replaced whole-node loading, so removing fast membership filters without measurement may worsen disk I/O. `src/resolution/index.ts:488`, `:670`, `:690`, `:2628`.

| Option | Approach | Pros | Cons and risks | Effort/complexity | Expected benefit |
| --- | --- | --- | --- | --- | --- |
| A | Share a versioned compact immutable membership snapshot and byte-budget private caches | Cuts replication while preserving fast negatives | Building/invalidation cost; approximate filter must never produce false negatives | High | Lower peak RSS as worker count increases |
| B | Use batched indexed membership and canonical SQL-side narrowing with weighted local caches | Simpler ownership of truth | May trade CPU/RSS savings for encrypted-disk reads | Medium–high | Smaller retained heap without shared-memory protocol |

**Recommend A only if membership replication is measured as a dominant cost.** First sweep supported worker counts. Require pooled/sequential graph parity and report local reads alongside RSS on high-cardinality and name-collision fixtures.

#### CGIO-09 | Deferred reference post-passes can bypass batch memory bounds

**Confirmed, high confidence; frequency unmeasured.** Ordinary reference input is paged, but deferred refs and row IDs accumulate across pages and their post-passes hold additional result arrays. Live payload is O(D) for D deferred references. Impact is workload-dependent, not a blanket OOM claim. `src/db/queries.ts:4568`; `src/resolution/index.ts:2297`, `:2407`, `:2455`, `:4188`.

| Option | Approach | Pros | Cons and risks | Effort/complexity | Expected benefit |
| --- | --- | --- | --- | --- | --- |
| A | Store ordered `(phase, row ID)` work in SQLite and process keyset pages | Bounded memory and reusable progress state | More writes; must preserve ref and pass ordering | Medium–high | Fixed-size post-pass payloads and potential resume reuse |
| B | Byte-limit in-memory queue and spill ordered overflow only to encrypted storage | No extra DB writes on routine cases | Separate spill lifecycle; less durable without an extra protocol | Medium | Bounds peak in high-deferral cases |

**Recommend A only if profiling confirms pressure and the resume schema can reuse it; otherwise defer.** Verify edge/failure parity and interruption behavior on a deliberately dense fixture; confirm reduced RSS outweighs write amplification.

## Proposed stored-first and resume contracts

1. Start a run tied to workspace identity, source/mount or snapshot identity, scope and ignore fingerprint, extractor/grammar/schema compatibility, and a monotonically increasing generation. Keep existing `files` as the authority for indexed content. Add directory rows keyed by canonical relative path with parent, last trusted observation and completeness status; add work/run rows only for needed replay state. Materialize no source body in inventory tables.
2. Read small pages of stored candidates immediately while bounded parallel discovery refreshes necessary directory entries. Use a single writer, bounded queues, and a priority lane for known dirty files. Deduplicate by path/run and preserve deterministic extraction/commit ordering where it affects graph resolution. Revalidate an observation if source changes mid-run; directory mtime is a hint for membership, never proof that member contents stayed unchanged.
3. Only skip scanning a directory or statting a file using a trusted snapshot/delta token or change feed with continuity scoped to the checkout, or after a prior observation was proven current for that run. On unknown coverage, generation mismatch, overflow, config/sparse change, or mount failure, conservatively reconcile affected scope or abort publication. Do not use Git HEAD or directory mtimes alone as authority for a mutable working tree. Deletions require successful parent/subtree enumeration or authoritative tombstones. Do not conflate a partial generation with absence.
4. Commit graph effects and completion for each deterministic batch together. Use stable work identities and idempotent phase/batch markers, not a bare offset in a mutable listing. Resume only compatible work; requeue changed inputs and retain unfinished phases. Run final resolution/synthesis with their own invalidation conditions; keep the previous complete generation readable if staged publication is approved.
5. Bound JS memory by cursor page and queue bytes; avoid a heartbeat write for each unchanged file. For a complete feed with k changes, aim for change-proportional source operations plus indexed local lookups; full recovery and untrusted discovery remain O(N). New metadata and staging add SQLite write amplification: compare WAL, DB and scratch totals on the encrypted volume before adopting either.

## Lessons learned

An indexed-file row proves what was indexed, not that a remote source still matches; inventory enables cheap local traversal but only trustworthy source evidence avoids remote discovery. Make remote latency, encrypted SQLite writes and memory explicit, separately measured costs.
